--------------------------------------------------------------------------------
1. QUE HACE EL SISTEMA, EN UNA FRASE
--------------------------------------------------------------------------------

Recibe un pedido de corrida por HTTP ("procesa N ordenes con P productores, C
consumidores, buffer de tamanio T"), lanza esos hilos de verdad (Thread, no
Task), procesa las N ordenes en paralelo pasandolas por un buffer limitado
compartido, mantiene una cache del estado de cada orden que se lee y se escribe
concurrentemente, y devuelve las metricas de la corrida en JSON.

El objetivo NO es procesar ordenes: es EXHIBIR Y MEDIR dos tecnicas de
sincronizacion resolviendo los mismos dos problemas clasicos. El procesamiento de
la orden es computo numerico simulado a proposito (SimularProcesamiento), para
tener carga de CPU controlable via CantIteraciones sin depender de I/O.


--------------------------------------------------------------------------------
2. EL RECORRIDO DE UNA ORDEN, DE PUNTA A PUNTA
--------------------------------------------------------------------------------

Esta es la linea de vida completa. Cada flecha cruza (o no) una barrera de
sincronizacion:

  1. Un PRODUCTOR pide permiso para crear otra orden
       ContadorOrdenes.DescontarOrden()          <- atomico (Interlocked)
       Si devuelve false, ya se produjeron las N y el productor corta.

  2. El productor le pide un Id al generador
       GeneradorIdsOrden.ProximoId()             <- atomico (Interlocked)
       El Id es unico en toda la corrida.

  3. Crea la Orden y simula el computo (CreadoEn queda sellado en el constructor)

  4. ESCRIBE en la cache: Id -> Generada          <- ESCRITOR (exclusion mutua)

  5. Deposita en el BUFFER                        <- puede DEMORARSE si esta lleno
       (aca se sella InsertadoEnBufferEn)

     ................ la orden queda esperando en el buffer ................

  6. Un CONSUMIDOR la retira del BUFFER           <- puede DEMORARSE si esta vacio
       (aca se sella RetiradoDeBufferEn)

  7. ESCRIBE en la cache: Id -> EnProceso         <- ESCRITOR (exclusion mutua)

  8. Procesa (computo simulado), sella CompletadoEn y calcula la latencia

  9. La suma a la bolsa de completadas            <- ConcurrentBag

 10. ESCRIBE en la cache: Id -> Finalizada        <- ESCRITOR (exclusion mutua)

  Mientras todo esto pasa, en paralelo, los hilos LECTORES estan pidiendo
  LeerResumen() de la cache cada 50ms               <- LECTORES (concurrentes)

  Al final, CalculadoraMetricas toma la bolsa de completadas y arma el JSON.

  Fijate que hay DOS problemas de sincronizacion distintos conviviendo:
    - pasos 5 y 6   -> productor/consumidor con buffer limitado
    - pasos 4, 7, 10 y los lectores -> lectores/escritores sobre la cache
  Son independientes entre si y estan resueltos por separado.

LA IDEA ARQUITECTONICA CENTRAL: los actores (Productor, Consumidor, LectorCache)
dependen SOLO de las interfaces IBuffer e ICache. No saben si atras hay semaforos
o monitores. Por eso se puede cambiar la tecnica de sincronizacion sin tocar una
linea de la logica de negocio, y por eso las dos variantes son comparables de
verdad: corren exactamente el mismo codigo alrededor.

4. PROBLEMA A: EL BUFFER LIMITADO (productor/consumidor)
--------------------------------------------------------------------------------

EL CONTRATO (IBuffer): DepositarDato(orden) / RetirarDato() / EstrategiaBuffer.
Son bloqueantes: si no se puede, el hilo se DEMORA (no falla, no reintenta).

LAS DOS CONDICIONES DE SINCRONIZACION:
  - un productor no puede depositar si el buffer esta LLENO
  - un consumidor no puede retirar si el buffer esta VACIO
Y ademas, exclusion mutua sobre la estructura mientras se toca.

  --- VARIANTE (a): BufferSemaforos ---

  Estructura: arreglo circular de tamanio N, con dos indices (Libre para
  depositar, Ocupado para retirar), cada uno avanzando modulo N.

  Semantica de los semaforos:
    _vacio  arranca en N -> "cuantos lugares libres quedan".
            El productor hace Wait: si vale 0, el buffer esta lleno y se demora.
    _lleno  arranca en 0 -> "cuantas ordenes hay para consumir".
            El consumidor hace Wait: si vale 0, el buffer esta vacio y se demora.
    _mutexDepositar / _mutexRetirar -> exclusion mutua, uno por punta.

  La condicion NO SE VE en el codigo: vive adentro del contador del semaforo. Hay
  que reconstruirla mentalmente. Ese es el costo de legibilidad de esta variante.

  A cambio: como los mutex son DOS SEPARADOS, un productor y un consumidor pueden
  estar trabajando AL MISMO TIEMPO sobre puntas distintas del arreglo. Mas
  paralelismo real.

  --- VARIANTE (b): BufferMonitores ---

  Misma estructura exacta (arreglo circular, Libre, Ocupado) a proposito, para que
  la comparacion sea honesta: lo unico que cambia es la sincronizacion.

  Semantica: UN solo monitor (_monitor) y un contador explicito ordenesEnBuffer,
  que es el equivalente visible de lo que en la variante (a) llevan por dentro los
  semaforos.

    DepositarDato : while (ordenesEnBuffer == Capacidad) Monitor.Wait
    RetirarDato   : while (ordenesEnBuffer == 0)         Monitor.Wait
    las dos, al terminar: Monitor.PulseAll

  POR QUE while Y NO if -> es la esencia de SIGNAL-AND-CONTINUE. El que hace
  PulseAll NO entrega el monitor: sigue el, y lo suelta recien al salir del
  lock(){}. El despertado no arranca con la condicion garantizada: tiene que
  volver a competir por el lock, y para cuando lo consigue, otro hilo pudo haber
  entrado y roto la condicion de nuevo (por ejemplo, otro consumidor se llevo la
  unica orden que habia). Con if, ese hilo seguiria de largo y leeria una posicion
  invalida. Con while, la reevalua y se vuelve a dormir si hace falta.

  POR QUE PulseAll Y NO Pulse -> sobre el MISMO monitor esperan productores y
  consumidores, que tienen condiciones DISTINTAS (lleno / vacio). Con Pulse
  despertas a UNO cualquiera: si le toca a un productor que tampoco puede avanzar,
  ese se vuelve a dormir y la senial SE PIERDE para el consumidor que si podia ->
  todos dormidos, deadlock. PulseAll cuesta que todos reevaluen, pero no pierde
  seniales. (Con colas de condicion separadas se podria usar Pulse; con un solo
  monitor, no.)

  Costo: hay UN solo lock, asi que productores y consumidores se serializan entre
  si. Menos paralelismo que la variante (a).

  --- EL TRADE-OFF, QUE ES LO QUE HAY QUE CONTAR EN EL INFORME ---

  Semaforos : condicion implicita (escondida en el contador), mas dificil de leer,
              mas paralelismo (dos mutex, dos puntas).
  Monitores : condicion explicita y a la vista (while ordenesEnBuffer == ...), se
              entiende de una, menos paralelismo (un solo lock).

  Claridad contra paralelismo. Ese es el eje de la comparacion cualitativa del
  punto 6 de la propuesta.

5. PROBLEMA B: LA CACHE (lectores/escritores)
--------------------------------------------------------------------------------

EL CONTRATO (ICache):
    Escribir(id, estado)   -> ESCRITOR: acceso exclusivo, nadie mas adentro.
    Leer(id)               -> LECTOR: varios a la vez. null si no esta registrada.
    LeerResumen()          -> LECTOR: conteo por estado de toda la cache.

QUIEN ES QUIEN: Productor y Consumidor son ESCRITORES (marcan Generada, EnProceso,
Finalizada). LectorCache es LECTOR puro. O sea, los mismos hilos que hacen el
productor/consumidor son, del otro lado, los escritores de este segundo problema.

LA REGLA: N lectores a la vez, o 1 escritor solo. Nunca mezclados.

  --- EL PUNTO FINO DEL DISENIO (vale para las TRES implementaciones) ---

  El lock/semaforo protege SOLO LOS CONTADORES, no el diccionario. El acceso real
  a _estados se hace AFUERA de la region protegida.

  Por que: si el diccionario se leyera adentro del lock, los lectores se
  serializarian entre si y se perderia todo el sentido del problema, que es
  justamente que N lectores lean EN PARALELO. Lo que se sincroniza es el permiso
  para entrar, no el acceso al dato.

  Es seguro porque el protocolo garantiza que mientras hay lectores adentro no hay
  ningun escritor, y viceversa. El Dictionary soporta lecturas concurrentes; lo
  que no soporta es lectura y escritura a la vez, y eso es exactamente lo que el
  protocolo impide.

  --- LAS DOS POLITICAS ---

  PREFERENCIA A LECTORES: el lector solo se frena si hay un escritor ACTIVO. No
  mira si hay escritores esperando: les pasa por arriba. Consecuencia: mientras
  entre un lector atras de otro, el escritor nunca ve lectoresActivos == 0 y puede
  morir de hambre (INANICION). No es un bug: es la definicion de la politica.

  JUSTA: el lector tambien se frena si hay escritores DEMORADOS. Les cede el paso.
  Con eso el escritor tiene garantia de avanzar.

  La diferencia esta en UNA condicion. En CacheSemaforosJusta.Signal(), la rama de
  despertar lectores pide "escritoresDemorados == 0". Esa sola condicion es toda
  la politica justa.

  ESTO ESTA MEDIDO. Con 6 lectores en loop cerrado y 1 escritor, escrituras
  logradas en 2 segundos:
        preferencia a lectores :     166
        politica justa         :  24.440      (~147x)
  Es el numero que hay que graficar en el punto 7 de la propuesta.

  --- LAS TRES IMPLEMENTACIONES ---

  CacheSemaforosLectores (semaforos, preferencia a lectores)
      El clasico: un mutex sobre el contador de lectores, y el PRIMER lector que
      entra toma _colaEscritores, el ULTIMO que sale lo suelta. O sea, los lectores
      "como grupo" se comportan como un solo escritor frente a los escritores.
      [OJO: LeerResumen todavia tira NotImplementedException. Ver restante.txt.]

  CacheSemaforosJusta (semaforos, PASSING THE BATON, politica justa)
      La tecnica del baton: hay un testigo (_entrada) y colas donde se duermen los
      demorados (_colaLectores, _colaEscritores). Quien tiene el testigo y termina
      de tocar los contadores llama a Signal(), que decide A QUIEN pasarselo:
        1) si se puede leer y hay lectores demorados -> despierta a UN lector
        2) si no, si se puede escribir y hay escritores demorados -> UN escritor
        3) si nadie puede avanzar -> suelta el testigo
      Se evalua EXACTAMENTE UNA rama: el baton se le pasa a UN solo hilo.

      La propiedad clave, y la diferencia semantica mas importante contra los
      monitores: el que despierta ARRANCA CON EL TESTIGO EN LA MANO y con la
      condicion YA GARANTIZADA. No tiene que reevaluar nada. Por eso aca no hay
      while: el que hizo el Signal ya verifico la condicion por el.

      El despertar en cascada de lectores sale gratis: cada lector que entra vuelve
      a llamar a Signal(), que despierta al siguiente, y asi hasta vaciar la cola.

  CacheMonitores (monitores, signal-and-continue, preferencia a lectores)
      Mismo problema con lock + Monitor.Wait/PulseAll. Aca SI hay while, por lo
      mismo que en BufferMonitores: PulseAll no cede el monitor, el despertado
      compite de nuevo y la condicion pudo cambiar.
      LiberaLeer solo hace PulseAll si fui el ULTIMO lector: es el unico caso en el
      que un escritor demorado puede llegar a pasar su while. Avisar antes seria
      despertar a todos al pedo.

  --- SEMAFOROS vs MONITORES EN LA CACHE, EN UNA LINEA ---

  Passing the baton: mas dificil de escribir (hay que razonar a quien le paso el
  testigo en cada salida), pero deja la politica EXPLICITA en una sola funcion
  (Signal), y no desperdicia despertadas: el que se despierta siempre puede
  avanzar.
  Monitores: mas facil de escribir, la condicion se lee directo, pero PulseAll
  despierta a todos para que la mayoria se vuelva a dormir (despertadas
  desperdiciadas), y la politica queda desparramada en las condiciones de los
  while.

6. LAS PIEZAS DE COORDINACION Y POR QUE EXISTEN
--------------------------------------------------------------------------------

  ContadorOrdenes  (Interlocked.Decrement)
      Responde "quedan ordenes por producir?". Con varios productores compitiendo,
      un contador comun con un if daria race condition (dos productores leyendo 1
      y produciendo los dos). Interlocked lo resuelve en una sola operacion
      atomica: decrementa Y devuelve el valor. El que se lleva el <= 0, corta.
      Por eso el total producido es EXACTAMENTE N, sin importar cuantos productores
      haya.

  GeneradorIdsOrden  (Interlocked.Increment)
      Reparte los Id. Mismo razonamiento: atomico, asi dos productores nunca se
      llevan el mismo numero. Es lo que hace que "cada orden se procesa exactamente
      una vez" sea una propiedad AFIRMABLE: sin identidad unica, no hay forma de
      contar.
      No es estatico a proposito: se instancia uno por corrida, asi cada ejecucion
      arranca en 1 y las corridas de las mediciones no se contaminan entre si.

  Orden.PoisonPill()  (la "orden veneno")
      Una orden ficticia con esFin = true. Es el mecanismo de TERMINACION. Ver el
      punto 7, que es la parte mas sutil del sistema.

  ConcurrentBag<Orden> _ordenesCompletadas
      Donde los consumidores tiran las ordenes terminadas. Es concurrente porque
      varios consumidores agregan a la vez. No necesita orden: la calculadora
      despues ordena lo que necesita.

7. COMO TERMINA EL SISTEMA (el protocolo de terminacion)
--------------------------------------------------------------------------------

Esta es la parte mas sutil y merece explicarse bien, porque es donde estaria el
deadlock si estuviera mal.

EL PROBLEMA: el consumidor corre en while(true) y se bloquea esperando que haya
algo en el buffer. Cuando ya no quedan ordenes, se queda dormido PARA SIEMPRE
esperando una orden que nunca va a llegar. No alcanza con "avisarle" por una
variable, porque no la va a leer: esta dormido adentro del buffer.

LA SOLUCION: hay que DESPERTARLO POR EL MISMO CANAL POR EL QUE ESPERA. O sea,
darle una orden. Pero una orden falsa, que signifique "cortala".

LA SECUENCIA (ConfigurationRunService.EjecutarSemaforos):

  1. Se lanzan productores, consumidores y lectores.
  2. Se hace Join de los PRODUCTORES. Cuando vuelve, hay una garantia fuerte:
     las N ordenes reales YA ESTAN TODAS DEPOSITADAS en el buffer.
  3. Recien AHI se depositan C ordenes veneno (una por consumidor).
  4. Se hace Join de los CONSUMIDORES. Cada uno agarra una veneno y corta.
  5. Se cancela el token de los lectores y se los espera.

POR QUE ES CORRECTO (el razonamiento completo):

  - Cada veneno la consume EXACTAMENTE UN consumidor: al retirarla del buffer, la
    orden se saca (el indice avanza), no queda para otro. C venenos frenan
    exactamente C consumidores. Ni de mas ni de menos.

  - NINGUNA ORDEN REAL QUEDA SIN PROCESAR. Y esta es la clave: el buffer es FIFO.
    Como los venenos se depositan DESPUES del Join de los productores, todas las
    ordenes reales ya estaban adentro, o sea ANTES en la fila. FIFO garantiza que
    salen todas antes que cualquier veneno. Cuando un consumidor ve un veneno, es
    porque no quedaba ni una orden real.

    ---> EL ORDEN DE ESAS DOS LINEAS ES LO QUE HACE QUE FUNCIONE. Si los venenos
         se depositaran antes de que los productores terminen, un consumidor podria
         cortar mientras todavia quedan ordenes reales por venir -> ordenes sin
         procesar, y encima podrian quedar productores bloqueados con el buffer
         lleno y sin consumidores. Deadlock.

  - Los lectores no necesitan veneno porque no esperan sobre el buffer: esperan
    sobre un Thread.Sleep y un CancellationToken. Se cortan con Cancel(), que es
    el mecanismo que corresponde a como esperan.

  DETALLE: el veneno lleva Id = -1 y NUNCA se escribe en la cache, porque el
  consumidor hace el break ANTES de tocarla (Consumidor.cs: if (orden.esFin) break;).
  Si se escribiera, meteria un Id fantasma en el resumen.

8. UN ORDENAMIENTO QUE NO SE VE PERO SOSTIENE TODO
--------------------------------------------------------------------------------

En Productor.GenerarOrdenes(), estas dos lineas estan en este orden y NO se pueden
dar vuelta:

        _cache.Escribir(orden.Id, EstadoOrden.Generada);   // primero
        _buffer.DepositarDato(orden);                      // despues

POR QUE. Apenas la orden entra al buffer, un consumidor la puede retirar
INMEDIATAMENTE y escribir EnProceso. Si el productor escribiera Generada DESPUES
de depositar, se podria dar esta intercalacion:

        productor : deposita la orden
        consumidor: la retira y escribe  Id -> EnProceso
        productor : escribe              Id -> Generada     <-- PISA el EnProceso

La orden quedaria marcada como Generada cuando en realidad ya se esta procesando:
un lost update. El resumen de la cache mostraria estados que no son. Escribiendo
Generada ANTES de depositar, el consumidor no puede existir todavia para esa
orden, y la secuencia Generada -> EnProceso -> Finalizada queda garantizada.

Es un caso lindo para el informe: una race condition que no se arregla con un
candado sino con el ORDEN de las operaciones.

(La misma logica aplica del lado del consumidor: EnProceso se escribe apenas se
retira, y Finalizada recien despues de procesar.)

9. LA INSTRUMENTACION Y LA MEDICION
--------------------------------------------------------------------------------

Cada Orden lleva 4 sellos de tiempo, y cada tramo entre ellos significa una cosa
distinta:

    CreadoEn            <- constructor: el productor la creo
    InsertadoEnBufferEn <- adentro de DepositarDato
    RetiradoDeBufferEn  <- adentro de RetirarDato
    CompletadoEn        <- el consumidor termino

  CreadoEn -> CompletadoEn              = LATENCIA extremo a extremo (lo que pide
                                          la propuesta)
  InsertadoEnBufferEn -> RetiradoDeBufferEn = cuanto espero EN EL BUFFER. Este es
                                          EL indicador de si sobran productores o
                                          faltan consumidores.
  RetiradoDeBufferEn -> CompletadoEn    = trabajo real del consumidor. Deberia ser
                                          parecido en las dos variantes: si no lo
                                          es, la diferencia es costo de
                                          sincronizacion.

  Los sellos del buffer se ponen ADENTRO de la region critica, o sea que miden el
  momento real en que la orden entra/sale, no cuando el hilo pidio entrar.

  CalculadoraMetricas arma con eso el throughput, las latencias y el P95. Se usa
  P95 y no solo promedio porque el promedio esconde la cola: un par de ordenes muy
  lentas (justo las que la sincronizacion demoro) lo inflan sin que se vea el
  problema.

  POR QUE LOS Console.WriteLine ESTAN COMENTADOS: la consola tiene un lock interno
  propio. Un print por orden serializa TODOS los hilos y pasa a dominar el tiempo
  total. Se terminaria midiendo la velocidad de la consola y no la de la
  sincronizacion, que es el objeto entero del trabajo.

10. LOS INVARIANTES DEL SISTEMA (esto es lo que los tests van a afirmar)
--------------------------------------------------------------------------------

Escritos como propiedades verificables. Cada uno deberia ser un test:

  I1. Se producen EXACTAMENTE N ordenes.            (lo garantiza ContadorOrdenes)
  I2. Todos los Id son distintos, y son 1..N.       (lo garantiza GeneradorIdsOrden)
  I3. Se procesan EXACTAMENTE N ordenes: ninguna se pierde y ninguna se duplica.
      (lo garantiza el buffer + el protocolo de terminacion FIFO)
  I4. El buffer nunca guarda mas de Capacidad ordenes ni retira de uno vacio.
  I5. En la cache nunca hay un escritor con otro hilo adentro.
  I6. Toda orden termina en estado Finalizada.
  I7. La corrida siempre termina (no hay deadlock), incluso con buffer chico y
      muchos hilos.
  I8. I1..I7 valen IGUAL para las dos variantes de buffer -> los tests tienen que
      ser parametrizados por IBuffer, no escritos dos veces.
  I9. Con la politica justa el escritor avanza aunque haya lectores permanentes.
      Con preferencia a lectores, NO (y eso es lo esperado, no una falla).

  Estado actual: I1..I7 e I9 ya se comprobaron a mano al terminar los monitores
  (20.000 ordenes, 8 productores, 8 consumidores, buffer de 5). Falta escribirlos
  como suite automatizada, que es lo que quedo para el final.

12. LA DEUDA ARQUITECTONICA MAS IMPORTANTE (hoy)
--------------------------------------------------------------------------------

Toda la arquitectura esta pensada para intercambiar implementaciones detras de
IBuffer e ICache... pero ESO NO ESTA CABLEADO. ConfigurationRunService tiene el
campo Buffer tipado como BufferSemaforos (el tipo CONCRETO, no la interfaz) y hace:

        Buffer = new BufferSemaforos(tamanioBuffer);
        _cache = new CacheSemaforosJusta();

hardcodeado. El enum PoliticasCache existe pero no se usa en ningun lado, y
Orden.TecnicaCache nunca se asigna.

Consecuencia concreta: BufferMonitores y CacheMonitores estan terminados y
verificados, pero NO SE PUEDEN CORRER DESDE LA API. La interfaz comun existe pero
todavia no se aprovecha.

Lo que falta es chico y es lo que destraba todo lo demas: tipar Buffer como
IBuffer, una factory que elija implementacion segun un parametro de
ConfiguracionRun, y usar el enum que ya esta escrito. Sin eso no hay comparacion
(punto 6 de la propuesta) ni mediciones (punto 7).
